# Cumulative capability agent loop

This is the operational state machine for the single active lineage:

```text
fixed validation(C0)
        │
        ▼
C0 ── B1 proposal/review/apply ──► C5 ── validation(C5)
                                      │
                                      ▼
                                    B2 … C10 … B3 … C15 … B4 … C20 … B5 … C25
                                                                               │
                                                                               ▼
                                                        validation(C25) → final lock
                                                                               │
                                                                               ▼
                                                           authorize + 60-trial replay
```

The active branch identifier is `cumulative`; operators do not pass a branch
argument. `--review-mode independent|human` selects who reviews the same
proposal bytes. It does not fork the checkpoint lineage.

## Invariants

Raw GT and audit records are not exposed. Approved training GT is projected into prediction-shaped exemplars and retained as cumulative memory.

- Training, validation, and final-test panels are disjoint and fixed.
- C0 is the original S0 pack as a real frozen checkpoint.
- Every batch has exactly five training protocols and exactly one parent.
- Every proposal is based on the immediately preceding checkpoint and its
  required validation aggregate.
- Approved training sources and ground truth are projected into both a
  deterministic, source-located root-error ledger and the next checkpoint's
  prediction-shaped exemplar memory after batch reveal.
- Validation contributes macro/count guidance only. It cannot contribute
  evidence references, examples, sequences, solved records, error details,
  synthetic fixtures, or pack text.
- A proposer, critic, or revision worker can read only its staged workspace.
- A reviewer never applies bytes. Application is deterministic and separately
  authorized.
- One proposal may receive at most one bounded revision.
- One five-protocol batch may propose at most two procedural/tool units and
  accept at most one.
- Every checkpoint carries both its cumulative procedural `pack/` and its
  cumulative approved-training `memory/`; exemplar counts are exactly 0, 5,
  10, 15, 20, and 25 at C0 through C25.
- C25 plus six validation aggregates is the predeclared endpoint.
- Final-test unsealing permanently disables proposals, applications, and new
  checkpoints.

Run a read-only preflight first, then repeat with `--authorize-migration`. Both

If that clean C0 predates exemplar memory, run the one-time preflight below and


It archives the prior manifest and C0 runtime, preserves the procedural pack
exactly, creates empty C0 exemplar memory, and never starts a batch or Harbor.

## 1. Validate the parent checkpoint

Each condition evaluates the same five validation protocols. The Harbor input
must be generated by the validation planner so its task bundle, checkpoint,
runtime, pack, integration, model, harness, and output identities are pinned.
Raw validation results must live outside `$CAP_ROOT` and outside every worker
read boundary. Harbor schedules up to four independent protocols in parallel;
each trial still contains exactly one Codex agent and semantic retries remain
disabled.

If an infrastructure timeout interrupts only part of a panel, preserve the
original Harbor attempt and rerun only the unsuccessful protocol. Consolidate
the original and repair attempts deterministically before recording:

```bash
libstruct-libgen-capability-improvement bundle-validation-attempts \
  --canonical-config "$VALIDATION_CONFIG" \
  --attempt-root "$ORIGINAL_ATTEMPT_ROOT" \
  --attempt-root "$REPAIR_ATTEMPT_ROOT" \
  --output-root "$VALIDATION_BUNDLE_ROOT" \
  --created-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

The bundler accepts exactly one fully scored result for each fixed-panel
protocol, requires the same agent, mounts, instructions and artifacts across
attempts, and records source config/result plus exemplar-usage and passing
target-evidence-guard hashes. It rejects duplicate clean results, so a repair
cannot silently replace a completed trial.

After the five trials finish, record only the aggregate:

```bash
libstruct-record-validation \
  --experiment-root "$CAP_ROOT" \
  --checkpoint C0 \
  --result-root "$VALIDATION_C0_RESULT_ROOT_OR_BUNDLE" \
  --created-at "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
```

Repeat for C5, C10, C15, C20, and C25. The recorder refuses an overwrite,
symlink escape, wrong checkpoint mount, stale integration, duplicate raw run or
trial identity, nonfinite/out-of-range score, contradictory count, or an
in-experiment result root. The stored record contains aggregate metric means,
counts, and cryptographic provenance; it contains no per-protocol row.

The batch gates are fixed:

| Batch update | Required validation aggregate |
| --- | --- |
| B1 → C5 | C0 |
| B2 → C10 | C5 |
| B3 → C15 | C10 |
| B4 → C20 | C15 |
| B5 → C25 | C20 |

C25 validation is required for the final lock.

This is six evaluations of five protocols, or exactly 30 validation trials.
The aggregate for C25 closes the curve; it does not guide another capability
update.

## 2. Build one proposal

For B1–B3, point `--run-root` at the frozen five-protocol retrospective run.
For B4–B5, it is the terminal current-checkpoint prospective run and
`--c0-run-root` is the matched terminal C0 run.

```bash
CODEX_FORCE_AUTH_JSON=1 caffeinate -i libstruct-learn-capability \
  --experiment-root "$CAP_ROOT" \
  --batch B1 \
  --sources-root "$SOURCE_ROOT" \
  --groundtruth-root "$GROUNDTRUTH_ROOT" \
  --run-root "$B1_RUN_ROOT"
```

The command performs these resumable gates:

1. validates the active experiment, parent checkpoint, and required validation
   aggregate;
2. creates a revealed five-training-protocol packet and deterministic learning
   ledger;
3. copies only allowlisted packet artifacts, the parent pack, and the sanitized
   validation aggregate into a worker workspace;
4. runs Codex inside the read-confined, provider-only worker container using
   one read-only bind of the local `auth.json`; the staged root is read-only
   except for its nested `candidates/` and `outputs/` mounts;
5. validates the draft, candidate bytes, enforcement fixtures, leakage rules,
   and validation-guidance provenance; and
6. compiles a hash-pinned proposal.

Before the worker sees the ledger, deterministic filtering removes
infrastructure failures and evaluator, policy/source-scope, and ground-truth
defects. Metric mismatches sharing task, category, entity type, and process
cause collapse into one root event. Recurrence means presence in at least two
distinct training protocols. Excluded observations remain counts, not learned
examples.

The worker may emit at most two atomic `procedural_or_tool` units. A unit is
eligible for acceptance only when it cites a recurring root event, or when it
states a protocol-neutral general invariant and adds or changes the cited
negative synthetic regression fixture. A unit satisfying neither gate is
explicitly insufficient and cannot be accepted. The proposal worker does not
author the checkpoint's exemplar memory; the deterministic projector builds it
separately from approved training GT.

The worker cannot read `$CAP_ROOT`, source/ground-truth roots, Harbor result
roots, superseded history, or the host home directory. The host orchestrator
validates the workspace before and after execution.

## 3. Review, revise once, and apply

Independent review:

```bash
CODEX_FORCE_AUTH_JSON=1 caffeinate -i libstruct-complete-capability \
  --experiment-root "$CAP_ROOT" \
  --batch B1 \
  --review-mode independent \
  --groundtruth-root "$GROUNDTRUTH_ROOT" \
  --authorize-apply
```

Interactive human review:

```bash
libstruct-complete-capability \
  --experiment-root "$CAP_ROOT" \
  --batch B1 \
  --review-mode human \
  --reviewer-id seqmachines \
  --groundtruth-root "$GROUNDTRUTH_ROOT"
```

For each atomic change unit the human console shows the capability class,
generalized failure cluster, expected invariant, exact mutations, deterministic
fixtures, remaining model judgment, and unified diff. Available commands are:

- `accept`: use the exact proposed bytes;
- `reject`: retain the parent bytes;
- `modify`: request one bounded revision;
- `unresolved`: preserve uncertainty and make no change;
- `back`, `skip`, `status`, `quit`: navigate without losing decisions.

Every answer is atomically checkpointed. A `modify` answer normally launches
one isolated revision worker and then requires a fresh review of the revised
bytes. `--manual-revision` instead seeds a bounded editable workspace and
stops; only a later `--manual-revision-ready` can submit those bytes for the
fresh review. A second revision is rejected.

Both reviewer modes enforce the same admission budget: at most one accepted
procedural/tool unit per batch. The reviewer cannot override an insufficient
admission basis.

When the exact-byte decision is final, `--authorize-apply` permits the
orchestrator to:

1. verify proposal, baseline, candidate, decision, validation-feedback, and
   packet hashes;
2. apply only accepted atomic mutations;
3. run the manifest-driven synthetic suite in a networkless sandbox;
4. run validation and leakage checks;
5. emit the application record; and
6. verify the cumulative approved-training exemplar projection; and
7. freeze the next canonical C checkpoint with both `pack/` and `memory/`.

An instruction-only control must state the remaining scientific judgment. A
failed application cannot become a checkpoint. Rerunning the command reuses
completed hash-valid stages.

## 4. Advance through B1–B5

Use the exact parent/output mapping:

| Batch | Parent | Output | Phase |
| --- | --- | --- | --- |
| B1 | C0 | C5 | retrospective |
| B2 | C5 | C10 | retrospective |
| B3 | C10 | C15 | retrospective |
| B4 | C15 | C20 | prospective |
| B5 | C20 | C25 | prospective |

For B4/B5, create matched C0/current diagnostic configs without revealing
ground truth, finish both runs, and only then build the learning packet. Scores
belong to the checkpoint evaluated before the batch is revealed; C20 and C25
are learned from B4 and B5 respectively and are not unbiased evaluations on
those same protocols.

After freezing each output, run and record the fixed validation panel before
starting the next update.

The memory counts advance independently of procedural acceptance:

| Checkpoint | Cumulative approved-training exemplars |
| --- | ---: |
| C0 | 0 |
| C5 | 5 |
| C10 | 10 |
| C15 | 15 |
| C20 | 20 |
| C25 | 25 |

Validation data never enters the procedural pack or exemplar memory. Its
sanitized aggregate may guide the next procedural proposal only.

## 5. Lock and final test

The final lock requires these six exact directories:

```text
$CAP_ROOT/checkpoints/C0
$CAP_ROOT/checkpoints/C5
$CAP_ROOT/checkpoints/C10
$CAP_ROOT/checkpoints/C15
$CAP_ROOT/checkpoints/C20
$CAP_ROOT/checkpoints/C25
```

It also verifies six unique, checkpoint-bound validation result bundles for 30
total trials. The lock is written only at the canonical design path and closes
all capability mutation.

After a separate transfer-panel authorization, `plan-final-replay` creates six
matched job conditions over the same ten frozen protocols. Planning is rejected
before the lock, and manifest creation is the panel-unseal event. From that
moment the capability cannot change, regardless of replay performance.

The final replay contains exactly:

```text
6 checkpoints × 10 final-test protocols = 60 trials
```

`report-final` reports every protocol score, checkpoint macro means, changes
paired to C0, and paired-bootstrap intervals for T3 transition, state, and
typed-edge F1. C25 remains the predefined endpoint.

## Low-level commands

Low-level packet, workspace, compile, review, apply, and freeze commands remain
available for audit and CI. They enforce the same cumulative branch, validation
guidance, shared mutation lock, hash, isolation, and checkpoint gates. They are
not a bypass around the two normal commands.

The checkpoint is model-neutral. Any later framework may validate it, read
`runtime.json`, mount `pack/` and `memory/` read-only, execute the declared
compiler and unified audit, query at most three pseudonymous exemplars through
`memory/runtime/tools/query_exemplars.py`, and run the target-evidence guard.
No framework may reinterpret superseded A/H checkpoints as C lineage.
